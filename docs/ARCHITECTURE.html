1. Большая картина

Проект живёт в трёх фазах. Офлайн один раз (и после изменений в BandaStation) читаем исходники DM и .dmi и превращаем их в наши форматы. Сервер грузит прототипы и .dmm, держит авторитетный мир и всю логику. Клиент ничего не решает: рисует то, что пришло по репликации, и отправляет намерения (intents).

Главная идея. DM-типы не переписываются руками в Rust-структуры. Мы извлекаем переменные каждого DM-типа, превращаем их в прототипы с той же иерархией наследования (id = DM path, parent = DM parent) и спавним по ним сущности Bevy. Поведение (procs) пишется в Rust вручную, в ss13_game, по коду tg.

2. Карта крейтов

Слои сверху вниз: кто от кого зависит. Стрелка вниз читается как «использует то, что ниже». ss13_game, ss13_net, ss13_tgui, ss13_chat, ss13_admin и ss13_debug — это один крейт на две половины: фичи server и client. Общие типы данных (окна, HUD) лежат вне фич, поэтому обе половины используют один и тот же код сериализации.

Правила границ

  • Сетевая библиотека — только в ss13_net. Игровой код видит типы ss13_shared::protocol (ClientIntent, ServerMessage), а не QUIC.
  • ss13_world и ss13_atmos ничего не знают о рендере. ss13_render ничего не знает о сети: он рисует компоненты Appearance + Facing + TilePos, откуда бы они ни пришли.
  • Клиент никогда не видит серверные Entity, только свои NetId.
  • GPL-код SpacemanDMM изолирован в офлайн-инструменте, сам проект — AGPL-3.0-only.

3. Пайплайн ассетов

Три команды, порядок важен: импорт иконок использует dm_types.json, чтобы упорядочить атласы по использованию на картах, а convert берёт из манифеста GAGS-иконки.

Что происходит с ассетами в рантайме

Сервер на старте (MapLoadPlugin) 1. ProtoPlugin грузит прототипы из RON.
2. Читает .dmm из BandaStation, на каждый z карты создаёт z-уровень ss13_world.
3. Спавнит турфы и объекты по прототипам; правки переменных в .dmm применяются как overrides прототипа.
4. Иконки хранятся в прототипах строками и резолвятся по текущему манифесту один раз на пару (тип, правки). Поэтому после регенерации ассетов в прототипах не остаётся устаревших id.
5. Атмос читает TurfAir турфов, строит LevelAir. MetaStation: загрузка ~16 с в release (нативно)
Клиент 1. На старте читает только manifest.postcard.
2. Страница атласа запрашивается, когда спрайту впервые нужно состояние с неё. Декодируется не на главном потоке, пару кадров спрайт не рисуется.
3. Спрайты держат сильные handles, поэтому используемые страницы не выгружаются. Простаивающие больше 10 с выгружаются по LRU, когда загружено больше SS13_ATLAS_BUDGET_MB (256).
4. Для каждой страницы хранится AlphaMask (1 бит на пиксель) — пиксельные клики как в BYOND (mouse_opacity).
5. Звуки (.ogg) грузятся при первом проигрывании.

4. Сервер

Это Bevy-приложение без окна: MinimalPlugins + ScheduleRunnerPlugin. Всё состояние живёт в ECS. Порядок плагинов (crates/ss13_server/src/main.rs):

Один тик сервера (50 мс)

  1. PreUpdate. Приём: фреймы и датаграммы по каждой сессии превращаются в сообщения ClientIntent (Move, Click, Drag, UiAct, Say, клавиши…).
  2. Update. Игровые системы валидируют намерения (дистанция, видимость, кулдауны, права) и меняют компоненты. Атмос и машины работают на своих частотах по образцу tg-подсистем. process(dt) зависит от времени, а не от числа кадров.
  3. tgui. Пересчитывается ui_status открытых окон, данные отправляются при изменении или по таймеру.
  4. Репликация. Change detection по Networked: каждому клиенту уходят изменения того, что он видит.
  5. Метрики (по желанию): ss13_tick_seconds, ss13_atmos_*… Простой MetaStation: ~0.65 мс на тик в release.

5. Сеть и репликация

Interest management

  • Клиент получает Networked-сущности в Chebyshev-коробке вокруг своего Viewer и держит их, пока они не уйдут на KEEP_MARGIN за её край.
  • Поверх — line of sight, как в BYOND view(): сущности за стенами не отправляются вообще. Наблюдатели видят сквозь стены (Sight).
  • Свет и непрозрачность идут блоками 16×16 из более широкой коробки, чтобы тени на краю экрана были правильными.
  • Стоимость тика пропорциональна изменениям, а не размеру мира. Appearance хешируется один раз на изменение, клиенты получают интернированные AppearanceId.

Версия протокола

  • PROTOCOL_VERSION в ss13_shared/src/protocol.rs (сейчас 75). Поднимается при любом изменении формата: данные tgui-окна, новые сообщения, поля Appearance.
  • Клиент с другой версией получает отказ в handshake с причиной, а не тихо ломается.
  • Транспорты: client_quic/server_quic (wtransport, нативно) и loopback — тот же фрейминг в памяти; в браузере работает только он.
  • SS13_SIM_LATENCY_MS добавляет искусственную задержку для проверки предсказания.

7. tgui-окна

Как в BYOND, вся логика окна живёт на сервере. Клиент только рисует данные билдером, зарегистрированным под тем же именем интерфейса, что в tg (Vending, ChemMaster, Cargo, Wires…).

8. Веб-демо

Статический сайт без бэкенда. Сервер и клиент — два отдельных wasm-модуля в одной вкладке, связанные мостом через postMessage. Перезагрузка страницы сбрасывает всё.

Сборка: scripts/demo-package.sh (данные) → scripts/web-build.sh: release wasm → wasm-bindgen --target web → wasm-opt -Oz; страницы атласа в .qoi.gz, progress.html из docs/parity/. Те же данные упаковываются в Windows-демо (.github/workflows/demo.yml).

9. Процесс разработки

Паритет с tg docs/parity/<группа>/*.md — 29 групп (atmos, medical, kitchen, silicon…). Каждая механика tg имеет статус ✅/🟡/❌. Правило: ✅ ставится, когда сделан собственный механизм записи; чужие части переносятся в их группу. Очевидные баги tg не переносятся. scripts/parity-count.py пересчитывает итоги и генерирует PROGRESS.html.Сейчас: ✅ 260 · 🟡 756 · ❌ 1464
Волны агентов Ветка wave/<тема> от main в git worktree (space-station-rs-wt/*), по 2 агента одновременно. Агент реализует, сам вливает main и прогоняет gate, но не пушит и не трогает версию протокола. Координатор мержит по одной ветке, поднимает PROTOCOL_VERSION, регенерирует ассеты, прогоняет gate на main и пушит.

scripts/gate.sh — обязательная проверка перед пушем (~2–2.5 мин)
